# 그래픽 업그레이드 조사 — 2026-07-31 (v0.17 기준)

**조사 결과물. 아직 아무것도 구현하지 않았다.** 어떤 걸 할지는 교사가 고른다.

## 0. 지금 성능이 얼마나 남았나 (실측)

M5 맥 · 1600×900 기준으로 측정:

| 항목 | 값 | 해석 |
|---|---|---|
| 렌더 시간 (실외) | **1.18 ms** | 60fps 예산 16.6ms 중 7% |
| 렌더 시간 (교실 안) | **0.59 ms** | 4% |
| 삼각형 | 69,686 | 저폴리로선 넉넉 |
| 드로우콜 | 362 | 청크 병합 덕에 낮음 |
| 메시 | 819 | |
| 그림자 굽기 (2048) | 약 1 ms | NPC 회전 시 0.6초 스로틀로 재굽기 |
| 그림자 굽기 (4096 실험) | **3.3 ms** | 맥에선 여유, 크롬북은 위험 |
| WebGL2 | 지원 | 후처리 가능 |
| pixelRatio | 1.25 상한 | 첫 5초 fps<40이면 1.0으로 자동 강등 |

**결론: 맥에서는 여유가 크다. 다만 크롬북은 이보다 5~15배 느리므로, 무엇을 넣든
크롬북 1대에서 `SD.perf()` 실측을 거쳐야 한다.** (지금까지 크롬북 실측 미실시)

색 사용 현황: **서로 다른 색 199종**, 평균 채도 0.38, 밝은 색(명도 0.7↑) 83종.
→ 색이 흩어져 있어 "한 사람이 그린 그림"으로 안 보이는 것이 품질 체감의 큰 부분.

## 1순위 ⭐ 접촉 그림자(AO)를 버텍스에 굽기 — **런타임 비용 0**

**문제**: 지금 명암은 `baseOf()`의 "물체 자기 높이에 따른 그라디언트"뿐이다.
벽과 바닥이 만나는 선, 책상 밑, 방 모서리가 전혀 어둡지 않아서
모든 물건이 바닥에 **떠 있는 상자**처럼 보인다. 저폴리에서 가장 크게 티가 나는 부분.

**방법**: 청크 병합 시점(`geoAdd`)에 정점별로 주변 가림을 간이 계산해 버텍스 컬러에 굽는다.
이미 버텍스 컬러 파이프라인이 있으므로 **드로우콜·셰이더 비용이 전혀 늘지 않는다.**
(빌드 시간만 늘어남 — 현재 월드 생성이 1초 미만이라 여유 있음)

- 효과: 큼 (저폴리 → "입체" 느낌)
- 위험: **낮음**
- 작업량: 중간
- 크롬북 부담: **0**

## 2순위 ⭐ 색 팔레트 통일

199종 → 벽/바닥/나무/금속/천 등 **재료별 8~10색 팔레트**로 수렴하고
명도 단계를 규칙화(밝음/기본/그늘 3단).

- 효과: 큼 (그림책 톤이 잡힌다)
- 위험: 낮음 (색만 바뀜 — 구조 무관)
- 작업량: 중간~큼 (199곳 정리)
- 크롬북 부담: 0 (오히려 재질 캐시 적중률 ↑)

## 3순위 후처리 (SSAO + 약한 Bloom + 색보정)

`EffectComposer` 등 three.js addons를 `lib/`에 추가해야 한다(약 80~120KB, 외부 네트워크 의존은 여전히 0).
SSAO는 1순위의 상위호환이고 훨씬 정확하지만 **매 프레임 비용**이 든다.

- 효과: 큼
- 위험: **중간~높음** (크롬북 실측 전엔 미지수)
- 권장: **1순위를 먼저 하고, 크롬북 실측 후 판단**

## 4순위 만화 외곽선

- 인버티드 헐 방식 = 드로우콜 2배 → **반대**
- 깊이/노멀 기반 후처리 에지면 저렴 → 3순위와 묶어서 검토
- 아트 디렉션("마인크래프트로 지은 우리 학교")과는 잘 맞음

## 5순위 그림자 품질

4096 맵은 맥에서 굽기 3.3ms. 크롬북 환산 30ms+ → NPC가 돌 때마다 끊길 위험.
**대신 무료로 얻는 방법**: 맵은 2048 유지하고 **그림자 카메라 범위만 조이면**
같은 픽셀로 더 조밀해진다 (현재 220×190m → 190×160m 이면 실효 해상도 약 1.37배).
추가로 NPC 회전 재굽기 스로틀을 0.6초 → 1.2초로.

- 효과: 중간
- 위험: 낮음 (카메라 조이기만 할 경우)

## 6순위 하늘·원경

- 구름: 구 3개 → 납작한 저폴리 덩어리로 실루엣 개선
- 원경에 옅은 산 실루엣 한 겹 → 깊이감 (드로우콜 1~2)
- 효과: 중간 / 위험: 낮음
