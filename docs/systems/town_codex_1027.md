# 코덱스 네 관점 분석(10-27 · 아이·타학교 선생님·게임 기획자·코딩하는 사람 · 읽기 전용 · gpt-6-astra · 기준 커밋 2f21dc4)

**가장 먼저 손볼 것은 새 콘텐츠가 아니라 저장의 신뢰성, 첫 경험의 연결, 수업 운영 안내입니다.** 마을을 돌아다니며 배우는 재료와 실제로 달라지는 장면은 풍부합니다. 다만 이야기·하루 일정·잔치·보상·학급 저장이 서로 다른 약속으로 움직이는 부분이 있습니다.

지정한 문서와 코드를 읽기만 했습니다. 파일 수정이나 하네스 실행은 하지 않았습니다. 아래에서 **코드의 동작과 조건은 확인 사실**, 아이의 반응·실제 소요 시간·기기 성능에 대한 예상은 **추측**으로 구분합니다. 코드의 `min` 값은 예상 시간 자료이며, 실제 플레이 시간으로 취급하지 않았습니다.

**1. 🧒 초등 4학년 아이의 눈**

**① 좋은 점 셋**

- **처음 할 행동이 구체적이다.** 우리 집 현관 칠판 앞에서 시작하고, 첫 목표와 E 안내가 ‘쪽지 읽기’로 모입니다. “마을에서 알아서 놀아”보다 시작하기 쉽습니다. [town.js:6950][opening]
- **길 찾기와 글쓰기의 부담을 줄였다.** 프롤로그에서 갈 곳을 고르고, 안내를 따라 이동하고, 까닭을 카드로 채웁니다. 정답 없는 선택이라는 설명도 있습니다. [town_story.js:41][prologue]
- **화면을 단계적으로 열고 접근성 선택을 제공한다.** 시간표는 초반부터 전부 나오지 않고, 지도·도감 등의 공개 시점도 다릅니다. 글씨 크기·색 구분·흔들림 줄이기·읽어 주기 설정이 있습니다. 다만 읽어 주기는 기기에 한국어 음성이 있어야 합니다. [town.js:4166][hudgate], [settings.js:50][settings]

**② 가장 큰 문제 다섯**

**1) 처음 화면: ‘내가 놀기 시작하기까지’의 경로가 무겁다.**

마을 생성 과정과 시작 화면이 연결돼 있고, 저장 칸을 바꾸면 현재 마을을 정리하고 페이지를 새로 불러옵니다. 즉, 저장 칸 선택은 화면 내용만 바꾸는 동작이 아닙니다. [town.js:214][loading], [town.js:6966][slots]

**추측:** 크롬북에서 생성이 오래 걸리면, 아이는 시작 전에 기다리고 잘못 고른 칸을 바꿀 때 다시 기다릴 수 있습니다. 실제 대기 시간과 크롬북 FPS는 이번 검토에서 확인하지 않았습니다. ‘자동’ 화면 모드가 있다는 사실만으로 이 초기 대기가 해결됐다고 볼 수는 없습니다.

**2) 현관 첫 아침: 구경하러 움직였는데 이야기가 먼저 열린다.**

칠판을 읽지 않고 시작점에서 **14m보다 멀어지거나**, 조건을 만족한 1초 처리 횟수가 **40을 넘으면** 프롤로그를 자동 시작합니다. 헤매는 아이를 구하는 장치지만, 자유롭게 둘러보려는 행동과 구별하지 않습니다. [town.js:7344][tick]

**추측:** “집부터 구경하려는데 왜 갑자기 쪽지가 떠?”라는 반응이 나올 수 있습니다. 반대로 자동 시작을 없애기만 하면 무엇을 해야 할지 모르는 아이가 생깁니다. 지금 필요한 것은 자동 개입의 삭제보다 **구조 요청과 자유 탐색을 구분하는 방법**입니다.

**3) 프롤로그 → 1막: 방금 소개한 곳을 다시 소개한다.**

프롤로그에서는 도서관에 갔다가 우체국·소방서 등을 골라 새 친구를 데려갑니다. 바로 다음 이야기에서는 다시 도서관에서 만나 소방서와 우체국을 안내합니다. 방문 이력에 따라 “벌써 가 봤지?”라는 대사는 바뀌지만, 기본 이동 단계는 남습니다. [town_story.js:41][prologue], [town_story.js:55][actone]

**추측:** 첫 선택이 소방서나 우체국이었다면 “아까 했잖아”가 되기 쉽습니다. 아이의 선택을 기억하는 대사는 좋은데, **기억한 결과가 다음 행동까지 바꾸지는 못합니다.** 처음의 성취가 다음 장에서 새 능력으로 느껴지기 어렵습니다.

**4) 프롤로그 완료 직후: 다음에 해야 할 일이 다시 여러 갈래가 된다.**

이야기는 완료 후 다음 장으로 자동 연결하는 장치가 있고, 잔치는 프롤로그 완료만으로 첫 안내를 허용합니다. 잔치 창은 음식·꾸밈·공연·손님·안전의 다섯 갈래와 각각의 준비 방법을 보여 줍니다. [town_story.js:674][storyfinish], [town.js:5023][feastready], [town_feast.js:252][feastpanel]

시간표까지 첫 순간부터 모두 노출되는 것은 아닙니다. 그럼에도 **첫 장 완료 시점에 이야기와 장기 목표가 함께 관심을 요구하는 구조**는 확인됩니다.

**추측:** 휴대폰에서는 글과 버튼을 읽고 닫는 일이 이동보다 두드러질 수 있습니다. 실제 칩 겹침이나 가림은 화면으로 재현하지 않았으므로 현재 버그라고 단정하지 않습니다. 문제의 핵심은 칩 개수 자체보다 “지금은 어느 안내를 따르면 되는가”입니다.

**5) 첫 성공: ‘내가 해서 달라진 것’이 약하게 드러난다.**

프롤로그의 명시된 보상은 마을 수첩과 이야기 도장입니다. 새 친구가 장소를 기억했다는 반응도 있습니다. 하지만 그 다음 흐름은 다시 길 안내이고, 장기 목표인 잔치는 별도 날짜와 준비량으로 움직입니다. [town_story.js:49][prologue], [town_feast.js:215][feastplan]

**추측:** 수첩 수집을 좋아하는 아이에게는 보상이 되지만, “내가 뭘 바꿨어?”를 기대하는 아이에게는 첫 성공이 표시의 증가로 느껴질 수 있습니다. 다음 날 다시 하고 싶은 이유도 ‘다음 장이 있음’보다 **내일 확인할 변화**가 일찍 생길 때 더 선명할 것입니다.

**③ 고칠 방법 — 작게 시작하는 순서**

1. **프롤로그에서 고른 장소를 다음 장의 출발 조건으로 사용한다.** 같은 곳을 다시 방문하기보다 “친구가 이번에는 직접 찾아가는 것을 도와주기”처럼 역할을 바꿉니다.
2. **프롤로그 완료 화면에서 다음 목표 하나를 먼저 보여 준다.** 잔치는 수첩에 보관하고, 첫 안내는 이야기 완료 알림과 순서를 조정합니다.
3. **현관 자동 개입을 ‘도움 쪽지 도착’으로 한 단계 완화한다.** 칠판 위치와 읽기 행동을 다시 알려 주고, 강제 창 열기는 막힘이 지속될 때만 사용합니다.
4. **첫 선택의 결과를 현장에 남긴다.** 친구의 동선·장소의 작은 표시·다음 날 인사 중 하나만 바뀌어도 됩니다.
5. **실제 크롬북과 휴대폰에서 첫 화면부터 직접 걸어 검증한다.** 생성 대기, 칠판 접근, 글씨 확대 상태, 목표와 행동 버튼 가림을 우선 봅니다.

**④ 한 줄 총평**

**“처음 출발은 친절하지만, 첫 성공 뒤에 ‘아까 한 일’과 ‘다음에 할 일’이 더 자연스럽게 이어져야 또 들어오고 싶다.”**

**2. 🏫 처음 수업에 쓰려는 다른 학교 선생님의 눈**

**① 좋은 점 셋**

- **교과 활동으로 바꿀 만한 행동이 있다.** 장소를 찾아가고, 방위를 고르고, 선택의 까닭을 남기는 흐름이 코드에 들어 있습니다. 구경만 하는 가상 공간에 머물지 않습니다. [town_story.js:41][prologue], [town_story.js:55][actone]
- **교사용 진입 기능이 이미 있다.** 단원별 이야기 목록과 ‘바로 열기’가 있으며, 해당 이야기 시작 위치 근처로 이동시켜 줍니다. 수업마다 처음부터 진행할 필요는 없습니다. [town_story.js:830][teacher]
- **기본 운영에 도움이 되는 보호 장치가 있다.** 로컬 저장 칸, 저장 백업, 채팅 끄기, 입력 길이 제한 등이 있습니다. 사진 기능도 실제 카메라 촬영이 아니라 게임 화면을 캡처하는 구조입니다. [town_game.js:14][save], [main.js:1574][chat], [photo.js:9][photos]

**② 가장 큰 문제 다섯**

**1) 한 차시 운영: ‘바로 열기’는 있지만 ‘수업을 끝내는 틀’은 약하다.**

교사 화면은 이야기별 예상 분량과 시작 버튼을 제공합니다. 그러나 `teach()`는 현재 이야기를 쉬어 두고 다른 이야기를 실제 저장 상태에서 시작합니다. 독립적인 연습 판이나 수업 종료 시점까지 묶인 실행은 아닙니다. [town_story.js:830][teacher]

프롤로그의 `min:10`, 첫 1막 이야기의 `min:15`는 코드에 있지만, 이를 더해 **실제 아이가 그 시간 안에 끝낸다고 판단할 수는 없습니다.** [town_story.js:41][prologue], [town_story.js:55][actone]

**추측:** 교사는 시작 방법보다 “먼저 끝난 아이는 무엇을 하나”, “종 치면 어디서 멈추나”, “남길 학습 결과는 무엇인가”를 현장에서 더 많이 설명하게 될 수 있습니다.

**2) 성취기준 연결: 교과서 기획용 차시 ID와 공식 성취기준이 구분돼 있지 않다.**

`link`는 코드 주석상 **학년-단원-차시**이고, `UNIT`·`TOPIC`은 교과서 기획의 목차를 나타냅니다. 이것은 공식 성취기준 코드의 검증 자료가 아닙니다. 같은 교사 화면의 분류도 사회 중심입니다. [town_story.js:25][curriculum]

따라서 “사회와 연결된다”는 판단은 가능하지만, **특정 교육과정의 사회·과학 성취기준을 충족한다는 결론은 저장소 코드만으로 확인하지 못했습니다.**

**추측:** 다른 학교 교사는 자기 교과서의 해당 단원과 과학 활동의 관찰·판단 결과를 다시 찾아 연결해야 합니다.

**3) 아이 관리: 저장 칸 셋은 학급 관리 단위가 아니다.**

화면도 명확히 “저장 칸 셋은 이 기기에만”, 학급 번호로 들어오면 “내 판 하나”라고 안내합니다. 학급 기록은 기기별 복사·합치기를 안내합니다. 사진 앨범은 별도의 공통 IndexedDB에서 전체 사진을 읽으며, 조회 단계에 저장 칸별 필터가 없습니다. [town.js:6965][slots], [town_rec.js:61][record], [photo.js:6][photos]

**추측:** 공용 기기에서는 게임 판은 나눴는데 사진은 함께 보이는 등, 교사가 예상한 ‘아이별 분리’와 실제 분리가 달라질 수 있습니다. 세 칸을 학급 계정의 대체재로 설명하면 운영이 꼬입니다.

**4) 안전 설명: 로컬 이용·계정 저장·멀티플레이의 차이가 화면 설명에 충분히 반영되지 않는다.**

학급 기록 화면은 “서버로 보내지 않아요”라고 표시합니다. 하지만 계정 동기화 경로는 로컬 저장 JSON 전체를 서버로 보내며, 학급 기록 `rec`도 게임 상태 안에 있습니다. **계정 저장이 활성화된 경우 이 안내 문구와 전송 경로가 맞지 않습니다.** [town_rec.js:61][record], [town_cloud.js:26][cloud]

채팅에는 제한과 교사 끄기가 있지만 자유 입력도 존재합니다. 이야기에도 자유 문장 입력 경로가 있습니다. 이 장치들이 실명 입력을 원천 차단하는 것은 아닙니다. [main.js:1574][chat], [town_story.js:715][freewriting]

실제 개인정보가 전송됐다는 뜻은 아닙니다. **무엇을 어디에 저장하는지 교사가 정확히 설명하기 어려운 상태**라는 뜻입니다. 첫 화면에서 학교 이름을 숨기는 시험만으로 전체 공간의 익명화까지 검증했다고 볼 수도 없습니다. [town_open.cjs:22][openharness]

**5) 다른 학교 적용: 사진에서 마을로 만드는 절차는 있으나 교사 혼자 완료하는 도구는 아니다.**

문서는 사진을 자료로 옮기고 배포한 뒤 도면을 확인하는 제작 절차를 설명합니다. 한편 이야기의 장소 찾기는 `p.name === n`이라는 정확한 이름 비교이고, 프롤로그는 ‘작은 도서관’, 첫 1막은 여기에 ‘소방서’와 ‘우체국’을 요구합니다. [town.md:17][townworkflow], [town_story.js:563][placefind]

**확인 사실:** 건물 이름을 바꾸거나 해당 시설이 없는 마을을 만들면 일부 이야기의 이용 가능 여부도 바뀝니다.

**추측:** 다른 학교에서는 사진 준비보다 필수 장소 맞추기와 이야기 검증에 더 많은 도움이 필요할 수 있습니다. 개발 문서는 많지만, 처음 쓰는 교사가 따라 할 최소 절차와 개발자용 제작 절차를 나눌 필요가 있습니다.

**③ 고칠 방법 — 작게 시작하는 순서**

1. **교사용 한 장 안내를 만든다.** 접속 방식, 추천 이야기 하나, 종료 지점, 남길 결과물, 저장 확인, 막혔을 때 복귀 방법을 담습니다. 시간 배분은 실제 수업으로 검증하기 전까지 ‘제안’으로 표시합니다.
2. **저장 안내를 현재 모드에 맞게 바꾼다.** 로컬·학급 계정·멀티플레이에서 기록·사진·채팅의 저장 위치를 구분합니다.
3. **기존 `link` 옆에 검증된 교육과정 대응표를 별도로 둔다.** 활동, 필요한 증거, 아이의 판단, 관찰 가능한 결과를 함께 적고 과학도 같은 형식으로 연결합니다.
4. **공용 기기용 초기화·인계 절차를 정한다.** 게임 판, 사진, 설정 중 무엇이 공유되는지 명시하고 저장 성공을 확인한 뒤 사용자 전환을 허용합니다.
5. **다른 학교용 최소 마을 템플릿을 제공한다.** 표시 이름과 `library` 같은 장소 역할을 분리하고, 빠진 역할을 배포 전에 검사합니다.

**④ 한 줄 총평**

**3. 🎮 게임 기획자의 눈**

**① 좋은 점 셋**

- **하루를 마무리하는 구조가 좋다.** 하루 회고는 자신이 한 일과 마을의 변화를 모으고, 내일 기다리는 일을 다음 동선으로 연결합니다. ‘하루 한 바퀴’의 중심으로 삼을 만합니다. [town_day.js:104][day]
- **REWARD-1에는 실제 능력 보상이 있다.** 장갑·장화·물뿌리개·레시피·도시락 등은 숫자와 도장 이상의 기능을 제공합니다. 보상 판정도 `rwCheck`라는 공통 경로가 있습니다. [town_reward.js:13][reward], [town_game.js:110][rewardcheck]
- **행동이 장면으로 이어지는 사례가 이미 있다.** 잔치 준비물이 마당에 생기고, 밤 순찰의 일부 해결은 현장 변화나 다음 날 수리로 이어집니다. 네 기둥 중 ‘남는 변화’를 구현할 기반이 있습니다. [town_feast.js:233][feasteffect], [town_night.js:336][night]

**② 가장 큰 문제 다섯**

**1) 긴 목표: ‘첫 잔치’가 서로 다른 진행 체계에 걸쳐 있다.**

프롤로그는 첫 잔치 도우미 모집으로 시작하고, 이야기에는 장소 선정과 피날레가 있습니다. FEAST-1은 별도의 날짜·준비량·회차·기록으로 움직입니다. 이야기의 완료 조건과 FEAST의 날짜 조건은 같은 상태가 아닙니다. [town_story.js:24][curriculum], [town_story.js:44][prologue], [town_feast.js:215][feastplan]

**추측:** 아이는 “이야기를 끝내면 잔치인가, 날짜가 오면 잔치인가”, “내가 고른 잔치와 이 준비는 같은 일인가”를 구분하기 어렵습니다. 긴 목표로 쓸수록 두 체계의 관계를 더 명확하게 보여 줘야 합니다.

**2) 잔치 준비: 기여의 의미와 ‘다 준비했다’는 종료 상태가 약하다.**

`srcOf()`는 요리·나눔·물 주기·도움 등을 음식 준비로 묶습니다. 반면 실내 부탁 완료가 내보내는 `ent`는 이 대응표에 없습니다. 활동의 서사적 의미와 잔치 기여 여부가 항상 맞아떨어지지는 않습니다. [town_feast.js:62][feastmap], [town_enter.js:489][enter]

또한 `bestAsk()`는 준비가 모두 끝난 갈래를 제외하지 않고 가장 낮은 단계를 고릅니다. 전부 완료했을 때도 일상 안내에서 다시 준비를 권할 수 있는 구조입니다. [town_feast.js:224][feastnotice]

**추측:** “가게를 도왔는데 왜 잔치에는 안 보태져?”, “다 했는데 또 하래?”가 생길 수 있습니다. 이는 준비량의 문제보다 행동과 결과의 인과관계 문제입니다.

**3) 하루 계획: 시간을 쓰는 행동과 시계를 멈추는 행동의 경계가 학습되지 않는다.**

게임 시계는 패널·대화·여러 놀이 상태에서 멈춥니다. 읽는 속도로 손해 보지 않게 하는 것은 타당합니다. 다만 시간은 이동 중에 흐르고, 일부 활동을 고르거나 수행할 때는 멈추므로, **하루 계획의 비용을 시계의 흐름만으로 이해하기 어렵습니다.** [town.js:7342][clockpause]

활동별 시간 비용을 이미 갖는 부분도 있으므로 전부 무제한이라는 뜻은 아닙니다.

**추측:** 네 기둥 중 ‘계획’이 “어떤 일을 선택할까”보다 “이동 거리를 줄일까”로 좁아질 수 있습니다. 대화를 빨리 넘기게 만들지 않으면서 활동의 기회비용을 보여 줘야 합니다.

**4) 성장과 난이도: 실제 능력 보상과 외형 선택의 중요도가 섞인다.**

REWARD-1에는 유용한 능력이 있지만, 여러 기술의 같은 성장 지점에서 자전거·가방 색 선택이 반복됩니다. 예를 들어 일·요리·장사·탐험의 해당 선택은 새로운 전략보다 외형에 가깝습니다. [town_reward.js:18][reward]

**추측:** 성장의 큰 이정표처럼 제시했을 때 기대와 실제 변화가 어긋날 수 있습니다. 이야기 등불·기술 성장·승급·나의 길·잔치 준비가 함께 존재하므로, 플레이어가 “오늘 무엇이 가능해졌나”를 한 문장으로 잡기 어렵습니다.

**5) 콘텐츠 깊이: 실내의 외형 다양성이 판단의 다양성을 앞설 위험이 있다.**

실내 부탁은 최근 선택을 피하고 성공 누적 뒤 어려운 부탁을 내는 장치가 있습니다. 그러나 공통 실행은 부탁을 받고, 맞는 탁자·선반·자리를 찾아 E를 누르는 틀이 중심입니다. [town_enter.js:469][enterstart]

완료 횟수와 이력은 저장되지만, 완료 때 나타나는 소품 변화는 현재 실내 객체에 적용됩니다. 재입장 뒤에도 같은 장면 변화가 이어지는지와는 별개의 문제입니다. [town_enter.js:489][enter]

**추측:** 여러 건물을 처음 들어갈 때는 풍성하지만, 익숙해진 뒤에는 “다른 배경에서 같은 찾기”가 될 수 있습니다. `town_lessons.md`와 `town_depth.md`가 요구한 ‘여러 번 해도 달라지는 판단’은 장소 수로 대신할 수 없습니다.

**③ 고칠 방법 — 작게 시작하는 순서**

1. **잔치의 완료 문구부터 고친다.** 준비가 끝난 갈래는 추천에서 제외하고, 전부 끝났으면 “준비 완료, 잔칫날 기다리기”를 보여 줍니다.
2. **첫 잔치의 관계를 하나의 진행 안내로 묶는다.** 이야기에서 정한 것과 날짜 기반 준비가 어떻게 이어지는지 표시합니다. 내부 상태 통합은 그 뒤에 해도 됩니다.
3. **잔치 기여에는 눈에 보이는 전달 과정을 붙인다.** 모든 활동을 자동 적립하기보다 “오늘 만든 빵을 잔치에 보내기”처럼 의도를 선택하게 합니다.
4. **읽는 시간은 멈추되, 선택한 활동의 시간 비용은 명시한다.** 준비물·활동 시간·내일 결과가 한 화면에서 이어지게 합니다.
5. **기존 활동 일부를 반복 플레이의 기준작으로 깊게 만든다.** 실내 부탁·순찰·농사처럼 이미 장면이 있는 활동부터, 관찰 근거와 선택 결과가 다음 방문을 바꾸게 합니다.

동물의 숲·스타듀밸리·젤다와의 비교는 개별 기능의 최신 현황을 확인한 비교가 아니라 **설계 관점의 추측**입니다.

- 동물의 숲을 기준으로 보면, 부족한 것은 장식 종류보다 **내 선택이 생활 공간에 오래 남는 감각**입니다.
- 스타듀밸리를 기준으로 보면, 부족한 것은 직업 수보다 **오늘의 준비가 내일의 선택을 바꾸는 연결**입니다.
- 젤다를 기준으로 보면, 부족한 것은 목적지 수보다 **주변에서 읽은 단서로 해결한 뒤 다른 상황에도 써먹는 경험**입니다.

**줄여도 되는 것**은 새 장소마다 붙이는 비슷한 찾기 과제, 같은 역할을 하는 성장 알림, 도장 수만 늘리는 보상입니다. 기존 성과를 없애기보다 선택형 수첩으로 옮기고, 공통 화면에서 차지하는 비중부터 줄이는 편이 안전합니다.

**4. 💻 코딩하는 사람의 눈**

**① 좋은 점 셋**

- **빌드 없이도 기능 경계를 만들려는 방향이 있다.** `createDay(A)`, `createFeast(A)` 같은 주입 방식과 모듈별 정리 함수는 추출·시험의 기반이 됩니다. 문제는 A 패턴 자체보다 계약과 호출 책임이 충분히 명시되지 않은 점입니다. [town.js:4993][dayinject], [town.js:5023][feastready]
- **저장 실패를 의식한 코드가 있다.** 일반 저장은 성공한 뒤에만 dirty를 해제하고 실패하면 재시도를 남깁니다. 백업·탭 소유권·되살리기도 이미 존재합니다. [town_game.js:145][saveflush]
- **성능과 가시성을 실제로 다룬 흔적이 있다.** 충돌과 레이는 공간 칸·재사용 배열을 사용합니다. 일부 생물 시험은 실제 렌더 픽셀 차이를 확인합니다. “모든 레이가 전체 메시를 훑는다”, “시험이 전부 내부 값만 본다”는 평가는 맞지 않습니다. [main.js:263][physics], [mapapi.js:62][ray], [town_close1.cjs:22][pixeltest]

**② 가장 큰 문제 다섯**

**1) 저장·삭제·전환: 일반 저장의 실패 처리가 파괴적 경로까지 이어지지 않는다. — 최우선**

확인된 경로는 다음과 같습니다.

- `delSave()`는 `:old` 백업 쓰기의 성공 여부를 확인하지 않고 본 저장과 `:bak`을 지웁니다.
- `newGame()`은 `flush(true)`의 실패 여부를 무시하고 삭제를 진행한 뒤 성공을 반환합니다.
- `slotGo()`도 저장 실패 여부와 무관하게 dispose와 reload를 진행합니다.
- `readSave()`는 본 저장이 깨진 JSON일 때 백업을 찾지만, 본 저장이 없으면 백업을 찾지 않습니다. `{}` 같은 객체도 정상 저장으로 받아들입니다.

근거: [town_game.js:14][save], [town_game.js:150][savereset], [town.js:6966][slots].

**코드상 확인된 위험:** 저장 공간 부족 등으로 보관 쓰기가 실패하면 ‘30일 되살리기’ 약속을 지키지 못하는 삭제 경로가 있습니다. 실제 데이터 손실을 재현한 것은 아닙니다.

버전 옮기기도 최상위 버전 처리와 각 하위 상태의 초기화·보관이 나뉘어 있습니다. 이전 값을 보관하는 것과 새 버전에서 계속 쓸 수 있게 옮기는 것은 다릅니다. [town_game.js:8][migration], [town_game.js:142][savemigrate]

**2) 시작·알림: ‘실행을 요청함’과 ‘성공해서 아이가 봄’이 같은 완료로 취급된다.**

`openKick()`는 프롤로그 시작 성공을 확인하기 전에 현관 시작 상태를 지우고 `P0G9`를 켭니다. 시작이 실패하면 그 함수 안에서 이전 상태로 돌아가지 않습니다. 현재 `ourtown`에서 실패한다고 재현한 것은 아니지만, 장소 부족·상태 변경 때 복구가 취약한 순서입니다. [town.js:6951][opening]

알림은 더 분명합니다.

- 자동 알림 대기는 한 칸이어서 새 알림이 이전 알림을 덮습니다.
- 직전 알림 뒤 **4초** 동안 바쁘다고 판단하지만, 대기 알림은 **3초**를 넘으면 버립니다.
- 잔치는 실제 표시 여부를 확인하기 전에 그날 안내 완료를 기록합니다.

근거: [town.js:122][say], [town_feast.js:246][feastsec].

일부 분위기 알림을 버리는 것은 괜찮습니다. 하지만 첫 안내나 마감처럼 다시 볼 필요가 있는 정보까지 같은 계약을 사용하면, **안내했다고 저장됐는데 아이는 못 본 상태**가 가능합니다.

**3) 구조: 파일 분리는 진행됐지만 연결 책임은 여전히 `town.js`에 집중돼 있다.**

현재 `town.js`는 **7,395줄**입니다. 시작 함수 안에서 세계 생성, 화면, 저장, 이야기, 모듈 주입, 루프, 종료가 이어집니다. 모듈별 `busy()` 조건도 조금씩 다르고, FEAST는 `GAME.tally`를 감싸 연결합니다. [town.js:119][townroot], [town.js:4993][dayinject], [town_feast.js:102][feastwrap]

수동 `?v=`와 registry 버전도 별도로 관리합니다. 현재 확인한 settings·photo import 버전은 맞아 있으므로 **지금 중복 로딩 버그가 있다고 주장하지 않습니다.** 다만 같은 파일의 쿼리가 달라지면 별도 모듈 URL이 되는 위험을 사람이 관리하는 구조입니다. [town.js:23][imports], [registry.js:36][registry]

**추측:** 다음 사람이 기능을 수정할 때 개별 모듈보다 “이 화면이 열렸을 때 어떤 시스템을 멈춰야 하는가”를 파악하는 데 시간이 더 걸릴 수 있습니다.

**4) 성능: 매 프레임 최적화와 별개로 주기 작업의 덩어리와 정리 누락이 남아 있다.**

1초 작업은 완전히 같은 시점에 몰아넣은 것은 아닙니다. 일부 타이머는 시차를 두었습니다. 그래도 `wxq`와 `emq`의 각 묶음 안에서는 많은 시스템을 연속 호출합니다. 방문 확인은 전체 장소를 훑고, FEAST는 주기적으로 키 목록·필터 결과·단계 JSON 등을 만듭니다. [town.js:6578][timerphase], [town.js:6985][been], [town.js:7344][tick], [town_feast.js:211][feastplan]

매 프레임에도 여러 모듈과 배열을 처리합니다. 하지만 이 사실만으로 병목이라고 확정할 수는 없습니다. **매 프레임 할당, 주기적 할당, 렌더 비용을 분리해 측정해야 합니다.** 레이 경로는 이미 공간 분할과 재사용 배열을 적용한 상태입니다. [mapapi.js:62][ray]

별도로, 채팅 생성 시 `setInterval(fade, 2000)`을 만들지만 UI 제거 함수가 이를 해제하지 않습니다. 이는 성능 추측과 구별되는 **코드상 타이머 정리 누락**입니다. 재입장을 반복할 때 누적될 수 있습니다. [main.js:1584][chatcleanup]

**5) 시험: 상태 시험이 실제 사용 성공까지 보증하는 이름으로 보고되는 곳이 있다.**

- OPEN 시험은 칠판까지 자연스럽게 걷지 않고 상호작용 위치로 순간 이동한 뒤 E를 누릅니다.
- ‘B로 자전거 타기’ 확인은 키 입력 대신 `SM_TOWN.bike(true)`를 직접 호출합니다.
- 1막 시험은 완료 상태와 단계 번호를 직접 설정합니다.
- 생태 효과 시험은 `log.ant`, `active`, `marks` 같은 값으로 ‘보이는 변화’를 판정합니다.
- OPEN의 휴대폰 경로는 `SHOTS`가 있을 때만 실행됩니다.

이 시험들은 상태 전이 시험으로는 유용합니다. 다만 **“칠판을 찾아 걸어갈 수 있다”, “화면에서 곤충이 보인다”, “휴대폰에서 누를 수 있다”의 증거는 아닙니다.**

고정 대기 시간과 내부 단계 직접 설정을 섞은 시험은 기기 속도나 자동 진행과 경쟁할 위험도 있습니다. 이번에 실제로 흔들리는 실패를 재현하지 않았으므로 이는 **시험 불안정성에 대한 추측**입니다.

**③ 고칠 방법 — 작게 시작하는 순서**

1. **저장·삭제·칸 전환의 성공 조건부터 통일한다.** 저장 실패 시 현재 판을 유지하고, 보관 성공을 확인한 뒤에만 삭제합니다. 저장 공간 부족·백업만 남음·유효하지 않은 객체·이전 버전 사례를 검증합니다.
2. **채팅 타이머 정리와 알림 완료 계약을 고친다.** 작은 수정으로 시작할 수 있습니다. 중요한 안내는 표시 성공 뒤 확인 상태를 남기고 수첩에서도 다시 볼 수 있게 합니다.
3. **OPEN을 명시적인 상태 전이로 정리한다.** 준비 → 칠판 대기 → 시작 요청 → 시작 성공을 분리하고, 실패하면 칠판 대기로 돌아갑니다.
4. **시험을 상태 시험과 사용자 경로 시험으로 나눈다.** 기존 빠른 내부 시험은 유지하되, 첫 아침·저장 칸 전환·대표 보상은 실제 입력과 화면 결과를 확인합니다. 고정 대기 대신 관찰 가능한 조건을 기다립니다.
5. **측정 후 작은 책임부터 추출한다.** 시작·저장 화면, 알림, 주기 작업 등록을 먼저 분리합니다. A 계약은 JSDoc 등으로 명시하고 `busy`·시간 정지 규칙과 이벤트 구독을 공통화합니다. 수동 캐시 버전은 우선 정적 검사로 불일치를 잡으면 되며, 이를 위해 빌드 시스템을 도입할 필요는 없습니다.

**④ 한 줄 총평**

**“최적화와 모듈화의 기반은 좋지만, 이제는 기능별 성공보다 저장·시작·알림·종료가 함께 지키는 계약을 강화해야 한다.”**
